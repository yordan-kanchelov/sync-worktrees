# ADR-0011: Command-line interface

- **Status:** Accepted
- **Date:** 2026-11-20
- **Source:** 139 code comments as of `5f17242`, moved here by [ADR-0001](./0001-record-decisions-in-adrs-not-comments.md)

## Context

The CLI is built with yargs. Flags keep backward-compatible spellings, subcommands share a parser, and output has to work both for a person at a terminal and for scripts.

## Decisions

Grouped by the file that implements them, source before tests. Each entry names the symbol it governs.

### `bin/node-version.js`

- **bin/node-version.js warnOnUnsupportedNode**: npm only warns (EBADENGINE) when engines.node is unmet and the warning scrolls past, so the bin shims check the Node major at startup and name the problem. The check warns instead of exiting because most commands still work on Node 22, which is just untested. A unit test keeps MIN_NODE_MAJOR in step with engines.node.

### `bin/sync-worktrees.js`

- **bin/sync-worktrees.js**: chalk honours FORCE_COLOR but not NO_COLOR and decides colour support once at import time, so the CLI bin shim translates NO_COLOR into FORCE_COLOR=0 before importing the bundle.

### `src/cli/doctor.ts`

- **DOCTOR_MIN_GIT_VERSION**: Git 2.36 is the oldest version the tool targets because `git worktree list -z` arrived there; older git falls back to the newline listing, which cannot represent worktree paths containing a newline. Older releases are reported as untested rather than refused.
- **DoctorCheck.check**: Doctor check identifiers (node, git, git-lfs, config, remote, worktree-dir, bare-repo-dir, disk-space, lock-dir, state-dir) are stable, since `doctor --json` consumers key off them.
- **repositoryUsesLfs**: Doctor only detects LFS use from HEAD of an already-synced repository; for one not synced yet it reports unknown (false), since fetching the tree just to find out is not a doctor's job.
- **runDoctorChecks**: When the git check fails, doctor skips every remaining check that runs git, since each would only repeat the git failure; only the config check is still reported.

### `src/cli/dry-run.ts`

- **runDryRun**: `sync --dry-run` plans each selected repository using the sync's own assessments, so it shows exactly the decisions a sync would take while changing nothing. It exits 1 when any repository could not be planned (an error or a lock that could not be taken at all); a lock held by another process is reported rather than failed, matching --run-once.
- **runDryRun**: In dry-run the plan is the output and logs are only for --debug; under --json stdout must carry nothing but the JSON, so loggers stay quiet even with --debug while warnings and errors still reach stderr.

### `src/cli/list.ts`

- **RepositoryDiskCounts**: In `list --json` disk counts, null means the value could not be read, or for trashEntries that the repository is in clone mode and has no trash; the error field explains, redacted, why a count that should be a number is null.
- **RepositoryDiskCounts.worktrees**: The listed worktree count includes only registered worktrees whose directory exists; in clone mode it is 1 once the clone exists.
- **ListedRepository**: Each element of `sync-worktrees list --json` always carries every key, using null for values that do not apply, so consumers never need to test for missing properties.
- **ListedRepository.branch**: The listed branch is set only for a clone-mode repository pinned to a branch; null means the clone tracks the remote's default branch.
- **countOnDisk**: List's disk counts use only local reads (`git worktree list` on the bare repository and a trash directory listing) with no fetch and no lock, so `list` stays safe to run next to a sync holding the repository.
- **countOnDisk**: Before the first sync there is no bare repository to ask, and nothing can have been checked out or trashed without one, so the worktree count is 0 rather than an error.
- **runList**: `sync-worktrees list` exits 1 when the config does not load or --filter matches nothing, reporting both on stderr so that with --json stdout stays empty rather than holding half a document.

### `src/cli/trash-command.ts`

- **TrashCliOptions.deprecatedFlag**: The pre-subcommand flag spellings of trash actions (such as --restore) keep working so scripts do not break, and each run names the replacement subcommand once.
- **stringArg**: yargs turns a repeated string option into an array. The same value given twice (easy to get from a shell alias) still means that value, while differing values are rejected as a usage error by checkBareTrash.
- **emptyTarget**: A trash id or keep-ref name given as an empty string, as from an unset shell variable, is a usage error; otherwise a destructive command would fall through to a listing and exit 0, giving a script a table and a success code.
- **trash command builder**: The bare `sync-worktrees trash` form owns its options with `global: false` so they stay off the subcommands: `--json` belongs to the listing, and the deprecated action flags (`--restore`, `--purge`, `--drop-keep-ref`, `--drop-all-keep-refs`, `--wait`) are hidden but still parse exactly as before.
- **trash command builder**: Mutual exclusion on the bare `trash` form uses `.check(checkBareTrash, false)` instead of yargs `.conflicts()`: yargs makes a conflicting key known to every subcommand, so `trash restore <id> --json` would parse and silently ignore `--json`. A non-global check runs for the bare form only.
- **BARE_CONFLICTS**: The bare trash flag form allows one action at a time; --json describes only the listing, so pairing it with an action would promise structured output that is never produced; and --wait concerns the repository lock, which only restore and purge take.
- **BARE_SINGLE_VALUE**: String options of the bare trash form given more than once with different values are a usage error, since there is no single value to act on; silently dropping them made `--purge a --purge b` a successful listing and `-f a -f b` act with no filter.
- **checkBareTrash**: In the trash conflict checks a boolean flag negated with --no-<flag> is treated as absent, the same as one never typed.
- **deprecationHint**: The deprecated trash flag hint is printed on stderr so piped stdout stays clean for scripts.
- **TrashCliError**: Failures the person running `sync-worktrees trash` can act on (wrong id, occupied destination, lock held elsewhere, declined confirmation) are reported as one line with exit code 1; anything else keeps its stack and reaches main().catch, because a stack is the only useful thing to say about a bug.
- **isPromptCancellation**: @inquirer installs its own SIGINT handler and rejects with ExitPromptError on Ctrl+C, so declining a prompt must be recognised as an expected cancellation. It is matched by error name because @inquirer/prompts does not re-export the class and @inquirer/core is not a dependency.
- **trashEntryLabel**: A trash row is labelled by branch when there is one; an orphan entry has none, so its original directory, relative to worktreeDir when inside it, is the only thing that identifies it.
- **printTrashRows**: The tab-separated rows printed since 5.2.0 are kept for a piped stdout so scripts such as `sync-worktrees trash | cut -f1` keep working: cli-table3 draws box characters and ANSI colour with no terminal detection. A terminal gets the table, and --json is the shape to build anything new on.
- **executeTrash**: Config loading throws plain Errors as well as typed ConfigErrors because a config file is user-supplied JavaScript; a config the user can fix is never a bug in the tool, so trash reports any load failure as one line like `list` and the sync command.
- **executeTrash**: Before the first sync there is no bare repository for simple-git to open, so trash lists nothing for such a repository and rejects every other action as not synced yet.
- **executeTrash**: Under --wait the lock budget is bounded (DEFAULT_CONFIG.LOCK_WAIT_MS), never an open-ended block, and is announced before waiting begins, but only for restore and purge, the operations that take the lock; a listing takes none.
- **shortKeepRef**: Trash command output names keep refs by the short name the commands accept, not the full ref path.
- **purgeTrashEntry**: After a purge the CLI prints only the minted keep ref and commit, because the reap path already logs the full recovery command as it mints the ref, and repeating it would duplicate the output.

### `src/constants.ts`

- **TERMINAL_CONSTANTS**: Most terminal emulators run the argv after DEFAULT_EXEC_FLAG as a program, but those in EXEC_FLAG_OVERRIDES take one string after -e, so '-e sh -c <cmd>' would run a bare sh or fail on -c. The overrides sit beside LINUX_CANDIDATES so the two cannot drift, and the explanation is kept above the statement because esbuild ships comments that lead object-literal members into the bundle.

### `src/index.ts`

- **RunOptions.quiet**: In one-shot runs, the quiet option limits output to warnings, errors and the final summary line.
- **RunOptions.filter**: RunOptions keeps the --filter value that narrowed the repositories so a config reload in the dashboard applies the same filter.
- **RunOptions.debug**: RunOptions keeps --debug so a config reload applies it to the reloaded repositories too.
- **runMultipleRepositories**: The global logger runs in debug mode when any repository has debug enabled, because its lines are about those repositories and --debug sets debug on all of them.
- **runMultipleRepositories**: Under --quiet the global logger stays at normal level because it prints the final summary line, which quiet keeps; everything else it emits under quiet is a warning or error, so only the opening banner is suppressed explicitly.
- **runMultipleRepositories**: The blank line before each repository header is printed through the global logger, because emitting it through the repository logger produced a line containing only the '[name] ' prefix; under --quiet the header is not printed, so neither is the blank line.
- **runMultipleRepositories**: Promise.allSettled preserves input order, so a rejected initialization is named from repositories[index]; the rejected task never returned a name, and its header line was printed whenever it started, which under parallelism is far from the error line.
- **runMultipleRepositories**: Per-action skips are informational and do not remove a repository that otherwise completed its sync from the success count; a failed repository is labelled by its failure only, not also as partially skipped.
- **runMultipleRepositories**: The run summary includes the skipped count only when it is non-zero, because '0 with clone-mode skips' on a worktree-only config described a mode not in use.
- **runMultipleRepositories**: Under --quiet the summary line is the only line a clean run prints, so it is not preceded by a blank separator line.
- **runMultipleRepositories**: --debug was applied to the repositories at load, but the dashboard reloads the config on r, so InteractiveUIService is told to apply debug to reloaded repositories as well.
- **runMultipleRepositories**: The startup sync is triggered last: InteractiveUIService's constructor already rendered Ink, which flushes App's mount effect (subscribing to events and emitting uiReady) synchronously, and addLog buffers in call order before the UI is ready, so the summary lines cannot be overtaken. It is not awaited so the cron jobs and UI keep running, and it matches the first cron tick except that logErrors is on, because a startup failure must be explained while the cron path stays quiet and retries next tick.
- **resolveConfigOrExit**: The 'no config file found' message builds its list of extensions from CONFIG_FILE_NAMES, the same constant discovery uses, so the message telling users what to create cannot drift from what the CLI actually searches for.
- **resolveConfigOrExit**: When the config path comes from the environment variable and the file is missing, the CLI names the variable explicitly, because a variable set in a shell profile and forgotten is invisible at the prompt.
- **runInit**: sync-worktrees init refuses to run without an interactive terminal, because its prompts can never be answered and the process would hang and then die with Node's unsettled top-level await warning.
- **runInit**: init checks whether the target file exists before prompting so the user is not asked several questions only to fail at the write; the atomic wx write remains the source of truth and closes the race between the check and the write.
- **runInit**: The init wizard writes a config the user never sees, so it loads it through ConfigLoaderService.buildRepositories, the same entry point a normal run uses, before reporting success.
- **runInit**: If the config init wrote does not load, the file is left in place because it holds the user's answers and is the only evidence of what went wrong, and with --force deleting it would also destroy the config it overwrote.
- **runFromConfigFile**: With --json, stdout carries only the JSON document, so the 'Using config' line goes to stderr where scripts will not parse it.
- **runFromConfigFile**: A --filter that matches no repositories exits with an error, matching list --filter, because it is almost certainly a typo and syncing zero repositories would exit 0.
- **runFromConfigFile**: A dry run is inherently one-shot and needs no terminal: it plans every selected repository, prints the plans and exits, so it runs before the interactive-terminal check.
- **runFromConfigFile**: The interactive dashboard reads keys in raw mode and draws on stdout, so without a terminal (systemd, docker, CI, stdin from /dev/null) the CLI exits with an error suggesting --run-once; otherwise Ink printed a raw-mode stack trace and exited 0 having synced nothing.
- **runFromConfigFile**: Errors escaping after the config has loaded are reported as 'Error running sync', not as a config loading error, because failures such as a service constructor rejecting a repository name or a render failing to mount are not problems in the config file.
- **main**: Trash commands restore and delete data, so a config discovered from a parent directory or the environment is named before anything happens, on stderr because stdout is the tab-separated or JSON listing scripts read.
- **isMainEntrypoint**: The main-entrypoint guard resolves symlinks on argv[1] with realpathSync so it works for npm/pnpm global bin shims and macOS /tmp -> /private/tmp; import.meta.url is already resolved.

### `src/services/logger.service.ts`

- **LoggerOptions.quiet**: --quiet drops info, debug and table output so only warnings and errors are printed, intended for one-shot runs under cron where every stdout line becomes mail.

### `src/services/worktree-sync.service.ts`

- **WorktreeSyncService.deleteKeepRefs**: A keep-ref drop that cannot start throws TrashError rather than a bare Error, because the CLI distinguishes 'the daemon holds the lock' by type and reports it as one line with exit code 1.

### `src/utils/cli.ts`

- **CliOptions.dryRun**: --dry-run computes and prints what a sync would do, changes nothing, and implies a one-shot run.
- **ROOT_FLAG_NAMES**: Root-command flags are listed explicitly because yargs' completion omits them: the default $0 command's builder never runs during completion.
- **namesTrashCommand**: argv names the trash command only when a trash word is not the value of the preceding flag, so list -f trash still filters on a repository named trash; a --flag=value carries its own value, leaving the next word free.
- **describeParseFailure**: Camel-case expansion makes yargs report one unknown flag under both spellings, so the names are collapsed to the typed one. Because the root is a default command, yargs' recommendCommands never fires and mistyped subcommands arrive as unknown positionals, so did-you-mean hints are computed here; names that are real commands or flags get no hint since they were misplaced, not misspelled.
- **describeParseFailure**: The old trash action flags (such as --purge) only work without a trash subcommand, so combining them with one gets a hint naming the new subcommand spelling.
- **completeArguments**: Shell completion adds the root command's flags at the top level, because a default command's builder only runs when executed so yargs never sees them, and removes the --c/--f spellings yargs derives from one-letter aliases, which no parser accepts.
- **checkConfigAndFilter**: --config and --filter require non-blank values because an empty --filter "$UNSET" would select every repository. Repeated --filter values are a union, but repeated --config is rejected since there is no single file to load.
- **parseArguments**: Kebab-case is the canonical flag spelling shown in --help; yargs camel-case expansion keeps camelCase spellings (`--runOnce`, `--dropKeepRef`) working as aliases, and strict() still rejects anything neither spelling names.
- **parseArguments**: In the yargs fail handler, a message returned by .check() also arrives as err, and a YError (Not enough arguments following) is likewise a usage error; only other errors are rethrown as exceptions.
- **parseArguments**: The CLI version comes from the build-time `__SYNC_WORKTREES_VERSION__` constant, because yargs would otherwise look for package.json next to its own install directory, which in a bundled or pnpm-installed copy is not ours.

### `src/utils/config-discovery.ts`

- **CONFIG_OPTION_DESCRIPTION**: Every CLI command shares one --config help text so no command describes config discovery differently.

### `src/utils/config-generator.ts`

- **serializeValue**: The generated config object is serialized as a plain JS object literal that is identical under ESM and CommonJS, so only the export statement depends on the detected module system.
- **readNearestPackageType**: The package type is read from the nearest package.json at or above the config directory using Node's own rule that the first package.json found wins. A missing, typeless, unreadable or unparsable package.json yields undefined and the generator falls back to ESM.
- **readNearestPackageType**: A malformed package.json stops the lookup, as it does in Node, so the generator never inherits a type from a higher package.json that Node would not apply.
- **detectConfigModuleSystem**: The generated config is written in the module system Node will load it under: .cjs and .mjs by extension, anything else by the nearest package.json type. This matters because with no type field Node's syntax detection still loads an ESM .js file, but an explicit "type": "commonjs" disables detection and the file fails with SyntaxError: Unexpected token 'export' (verified on Node 22 and 24).
- **detectConfigModuleSystem**: The extension check is case-sensitive on purpose because Node's extension handling and the config loader's .cjs require/import split are, so the generator and loader never disagree about an oddly cased path.

### `src/utils/error-summary.ts`

- **summarizeExpectedError**: Only git command failures and the tool's own typed errors are summarized to one line; anything else is treated as a bug and keeps its full inspected form and stack. simple-git messages carry git's whole stderr plus an inspected stack of internals (around 30 lines for a wrong URL), so the first fatal:/error: line is printed because it names the cause.
- **summarizeExpectedError**: A SyncWorktreesError message such as "Cannot fast-forward branch 'x'" says what failed but not why; git's reason lives on the cause, so its reason line is appended unless the message already quotes it.

### `src/utils/errors.ts`

- **configLoadErrorMessage**: The config loader already prefixes evaluation failures with "Failed to load config file: ", and CLI callers add their own label, so configLoadErrorMessage strips that prefix to avoid saying it twice and redacts secrets before the one-line report.

### `src/utils/interactive.ts`

- **promptForRepository**: Every init wizard answer is trimmed immediately because validators test value.trim(); storing the raw string let trailing spaces through, and path.resolve keeps them, producing unintended worktreeDir and repoUrl values. Trimming at the source also ensures the config-directory guard approves the same path that is saved.
- **promptForRepository**: In worktree mode the config file's own directory is rejected as worktreeDir: the default bareRepoDir .bare/<name> resolves against the config directory, so it would land inside worktreeDir and the next run would fail the bareRepoDir/worktreeDir overlap check.
- **promptForRepository**: In clone mode choosing the config directory only warns, because git clone will refuse the non-empty destination and the config directory is never empty; the user may move the config elsewhere.
- **promptForInitConfig**: The cron answer is stored trimmed because cron.validate accepts space padding but rejects tabs and non-breaking spaces, which trim removes; a pasted expression with such whitespace passed validation but the generated config then failed init's round-trip load. The wizard must store the exact string it validated.

### `src/utils/terminal.ts`

- **hasInteractiveTerminal**: The dashboard reads raw-mode keys from stdin and draws on stdout, and the init wizard prompts on both, so both must be TTYs. Under systemd, docker, CI or < /dev/null one is not, and Ink responds with a 'Raw mode is not supported' stack trace instead of an explanation, so the check runs first.
- **colorsEnabled**: FORCE_COLOR wins in either direction, as it does for Node and chalk; otherwise a non-empty NO_COLOR (no-color.org) disables colour; otherwise only a TTY gets colour.

### Tests

Why the tests that pin these decisions are built the way they are.

#### `src/__tests__/cli-sync-errors.test.ts`

- **runSync error reporting**: runSync reports failures that happen after the config loaded (a service constructor rejecting a repository name, a render that will not mount) as run errors, not as 'Error loading config file', so the person is not sent to edit a config that loaded fine. The single catch-all label was the regression these tests pin.
- **runSync error reporting**: A typed (actionable) failure such as ConfigValidationError is printed as its message only, without stack frames, because the message says everything the person can act on and frames of the tool's internals add nothing.
- **runSync error reporting**: When reporting a config load failure, the loader's own 'Failed to load config file' prefix is stripped so it is not repeated after the CLI's 'Error loading config file' label.
- **runSync terminal check**: Without an interactive terminal (systemd, docker, CI, stdin from /dev/null) Ink printed 'Raw mode is not supported' with a stack and the process exited 0 having synced nothing, so the CLI refuses to start the dashboard, exits 1 and points at --run-once.
- **ConfigLoaderService.buildRepositories debug option**: The --debug flag is passed to the config loader, which applies it, so every load of the config (not only the startup one) has debug enabled.
- **runSync error reporting**: An unexpected run failure (a bug in the tool) keeps its stack because one line says nothing useful, and the stack is scrubbed because a git failure quotes the remote URL it was given.
- **runSync --filter**: --filter narrows a sync the same way it narrows `list`, and a filter that selects no repository fails the run as a likely typo instead of running a clean no-op.

#### `src/__tests__/e2e/headless-cli.e2e.test.ts`

- **dashboard terminal check**: Without a TTY Ink printed 'Raw mode is not supported' with a stack and the process exited 0 having synced nothing, so the CLI refuses to start the dashboard, exits non-zero and points at --run-once.
- **init wizard terminal check**: Without a terminal the init wizard's prompts can never be answered, and the process sat idle then died with Node's 'unsettled top-level await' warning, so `init` refuses to run, exits 1 and writes nothing.

#### `src/__tests__/index.daemon.test.ts`

- **runMultipleRepositories daemon mode**: In daemon mode the startup sync and every cron tick go through InteractiveUIService, which owns progress plumbing, the parallelism limit and lazy initialization; unlike the run-once branch, the daemon branch never calls initialize() or sync() on the services directly.
- **runMultipleRepositories daemon mode**: A daemon runs until signalled, so the registered shutdown handler is its only exit path and must call the UI service's destroy (passing the fast flag); nothing else disposes the Ink render.
- **runMultipleRepositories signal handlers**: --runOnce installs signal handlers with exitAfterCleanupCode 130 so Ctrl+C reports an interrupted one-shot run; a daemon installs the plain handlers because being signalled is its normal end, not a failure.

#### `src/__tests__/index.run-once.test.ts`

- **run-once summary line**: The run-once summary line omits skip categories whose count is zero; only non-zero skip kinds are reported.
- **runMultipleRepositories run-once failure reporting**: Under parallelism the 'Repository: <name>' header prints whenever a task starts, so a bare 'Failed to initialize repository:' could not tell which repository died. The error names the repository, taken from the result's index since Promise.allSettled returns results in input order.
- **run-once repository header**: The blank line before a repository's header is not routed through the repository-prefixed logger, which otherwise printed a line containing only '[repo-a] '.
- **runMultipleRepositories run-level logger**: The run-level logger is created with the same debug setting as the repositories, so with debug on it also keeps full error detail.
- **runMultipleRepositories run-once branch**: syncOnStart defaults to true, so the guard against double syncing is the run-once branch itself: a one-shot run syncs inside runMultipleRepositories and never builds an InteractiveUIService that could start another startup cycle.
- **run-once --quiet**: --quiet exists for cron, which mails whatever reaches stdout: per-repository loggers go quiet, the banner is dropped, and only the single summary line remains.
- **run-once --quiet**: Under --quiet the summary line has no leading blank line, since that line only separated the summary from output --quiet drops.

#### `src/__tests__/init-round-trip.test.ts`

- **init wizard terminal check**: Without a terminal the init wizard's prompts can never be answered and the process idled then died with Node's 'unsettled top-level await' warning, so init refuses to start and exits 1.
- **init config round-trip**: The init wizard can write configs the loader later rejects (for example bareRepoDir on top of worktreeDir), so after writing it loads the file and exits non-zero with the loader error instead of printing 'Configuration saved', offering MCP registration and exiting 0.
- **init config round-trip**: When the generated config fails to load, init leaves the file in place because it holds the answers the user just typed and is the only evidence of what went wrong.
- **init config round-trip**: The init round-trip check runs buildRepositories, the same entry point the sync uses, so it also catches failures loadConfigFile alone misses, such as the cross-repository worktreeDir collision pass.

#### `src/__tests__/trash-cli.test.ts`

- **trash command**: Listing the trash takes no repository lock, so it must not print the lock-wait notice even under --wait; that notice belongs only to restore and purge, which do take the lock.
- **trash command listing**: cli-table3 draws box characters and ANSI colour with no terminal detection, so the trash listing renders a table only when stdout is a terminal. Down a pipe it keeps printing the tab-separated rows scripts have parsed since 5.2.0, which is also why the table is not a breaking change.
- **trash command listing**: The trash listing shows keep refs by short name rather than the full refs/sync-worktrees/keep/ path, because the short name is what the drop-keep-ref command accepts.
- **trash restore --wait**: A restore attempted while a daemon holds the cross-process repository lock would otherwise fail for a reason that clears within a minute, so --wait gives restore a lock wait budget.
- **DEFAULT_CONFIG.LOCK_WAIT_MS**: The --wait lock budget is bounded rather than blocking until the lock frees, so scripted runs terminate, and the user is told how long it will wait before waiting starts.
- **trash command error handling**: A rejected restore (wrong id, occupied destination, lock held elsewhere) is an ordinary outcome, so the trash CLI reports TrashOperationError as a single stderr line with exit code 1 rather than letting it reach main().catch with a stack.
- **trash command error handling**: The trash CLI's one-line error catch is deliberately narrow: unexpected errors such as a TypeError are bugs with nothing useful to say in one line, so they keep their stack and reach main().catch.
- **trash command prompts**: Ctrl+C at a confirmation prompt is how a destructive command is declined, and @inquirer answers it with its own ExitPromptError instead of letting the signal through; the CLI treats that error as a one-line cancellation rather than a crash with readline frames.
- **trash drop-all-keep-refs prompt**: The batch keep-ref drop prompt must warn that the commits become collectable by git gc and that the action cannot be undone; it is the only warning on an irreversible prompt, so the test pins it.
- **trash drop-all-keep-refs output**: Batch keep-ref drop results name refs by short name, the form the trash commands accept, never by full ref path.
- **trash purge**: Purge is a data-loss path and carries the same gate as keep-ref drops: both stdin and stdout must be TTYs plus a typed confirmation. A dedicated test redirects only stdin, since every other test sets both together and an && typo in the gate would pass them all.
- **trash purge**: A purge whose delete was refused leaves the entry listed and retryable, so the command exits with failure even though nothing crashed.
- **trash command**: Clone mode never removes its checkout, so it has no trash; the trash command rejects a clone-mode repository before any listing, restore or purge runs, as the README states.
- **trash command deprecated flags**: The old flag spellings (--restore, --dropKeepRef, --drop-all-keep-refs, --purge) keep working so scripts do not break, and each run prints a one-line replacement hint on stderr so stdout stays parseable.

#### `src/cli/__tests__/list.test.ts`

- **countOnDisk**: The list command's on-disk counting is read-only: listing a repository whose bare repo does not exist yet creates no worktree directory, bare repository, or trash.

#### `src/services/__tests__/logger.service.test.ts`

- **Logger quiet mode**: --quiet exists for cron, where every stdout line is mailed to someone, so quiet mode drops info, debug and table output and keeps only warnings and errors.

#### `src/services/__tests__/worktree-sync.repo-mutex.test.ts`

- **WorktreeSyncService.deleteKeepRef**: A keep-ref drop refused by the repository lock throws a typed TrashError so the CLI prints it as one line with exit code 1 instead of it reaching main().catch as an unhandled crash.

#### `src/utils/__tests__/cli.test.ts`

- **parseArguments**: `trash --json` conflicts with every trash action because --json describes the listing and an action produces no listing to describe.
- **parseArguments**: `trash --wait` is rejected with the listing and keep-ref drops it does not apply to, because --wait concerns the repository lock, which the listing never takes.
- **parseArguments**: Every subcommand must be listed in --help, because --help is the CLI's only reference shipped with the binary and an unlisted subcommand is invisible; the test pins the rule after trash went undocumented.
- **parseArguments**: The CLI version comes from the build-time define rather than yargs' package.json lookup, which starts at yargs' own install directory and, from a pnpm global install, finds pnpm's manifest and prints 'unknown'.

#### `src/utils/__tests__/interactive.test.ts`

- **promptForRepository**: Accepting the config file's own directory as worktreeDir made the generator write worktreeDir "./", put the default .bare/<name> inside it, and fail the next run's bareRepoDir/worktreeDir overlap check, so the wizard rejects it in worktree mode.
- **promptForRepository**: The worktreeDir answer is stored as path.resolve(value), relative to the cwd, so the config-directory guard must compare the same resolution or it rejects good answers and accepts bad ones.
- **promptForRepository**: Wizard validators test value.trim(), so answers must be stored trimmed too; path never strips trailing whitespace, so an untrimmed answer saved a different directory than the one validated and the generated config pointed init's round-trip load at it.
- **promptForRepository**: A relative worktreeDir must be trimmed before path.resolve, because resolve keeps the trailing space and every later sync would create a directory one character off from the one named.
- **promptForRepository**: The clone-mode warning compares worktreeDir with configDir via pathsEqual; against an untrimmed pasted path the comparison was false and the warning about the first clone failing never printed, so the answer is trimmed first.
- **promptForInitConfig**: cron.validate tolerates space padding but rejects tabs and non-breaking spaces, while the prompt validated value.trim(); a cron pasted from a crontab or doc page passed the prompt but failed init's round-trip load. The test spells the non-breaking space as a char code so the source stays ASCII.
- **promptForInitConfig**: The cron trimming is a real bug fix rather than cosmetic: the raw answer is what the config loader would receive, and node-cron refuses exactly the padded strings the prompt accepted.
- **promptForRepository**: Because the worktreeDir answer is trimmed on the way out, the config-directory guard must compare the trimmed value; reading the raw value would approve "<configDir> " and then store exactly configDir.
- **promptForRepository**: The repository URL check must validate the trimmed value; reading the raw value reported pasted URLs with a leading space as invalid even though the answer would be trimmed anyway.

## Consequences

Changing code covered by an entry here means updating the entry in the same pull request. An entry that no longer holds is deleted, or superseded by a new numbered ADR when the reversal is itself a decision worth keeping.
